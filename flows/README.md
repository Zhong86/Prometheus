# Langflow flows

This directory holds everything Langflow-side: custom components that wrap
external APIs, and reference prompt templates for the pure-Gemini reasoning
steps that use Langflow's *built-in* Prompt + Model + Structured Output
components instead of custom Python.

## Layout

```
flows/
├── Dockerfile                 # langflowai/langflow + google-search-results + tavily-python
├── Prometheus.json            # the wired DAG below — generated by build_flow.py
├── Prometheus.agents-backup.json  # original agent-based UI export (node templates for build_flow.py)
├── build_flow.py              # prompts/*.md + components → Prometheus.json (--push updates Langflow)
├── components/
│   └── prometheus/            # --components-path category folder
│       ├── academic_problems.py    # SerpAPI Scholar — runs planner queries
│       ├── public_friction.py      # Tavily — per-site searches (Reddit, HN, Capterra, Product Hunt)
│       ├── competition_analyst.py  # Tavily — runs each idea's competitor queries
│       ├── format_ideas.py         # multi-object Structured Output → one text block per idea
│       └── idea_report.py          # joins the 3 structured outputs by idea_id; one Astra doc per idea
└── prompts/                   # source of truth for every LLM node's config
    ├── query_planner.md
    ├── synthesize.md
    ├── competition_analysis.md
    ├── feasibility.md
    ├── spec_generator_prd.md   # not wired yet
    └── spec_generator_json.md  # not wired yet
```

## Pipeline: the LLM plans, the DAG executes

Each run researches a topic once and returns **3 distinct ideas**. Ideas are
scoped for a developer audience: every solution must be buildable by 1-3
developers with software, AI/automation, IoT or other tech.

There are no Agent nodes. Every LLM step is a **Structured Output** node
(`gemini-3.5-flash-lite`): the model writes the search queries, but the DAG
fixes the order of steps and each schema fixes the output shape. Each LLM
step is wired the full context it needs rather than just its predecessor's
output.

```
Chat Input (topic) ──┬──────────────────────────────┐
                     └─> Astra DB ─> Parser ─> negative_context
                                                    │
[LLM 1] Query Planner ── scholar_queries[], reddit_/hackernews_/capterra_/producthunt_queries[]
          │                          │
   Academic Problems           Public Friction           (no LLM)
          └────────────┬─────────────┘
[LLM 2] Synthesize ── 3 × { idea_id, evidence[], problem_statement, domain, target_user,
          │                solution_type, solution_approach, competitor_queries[] }
   Competition Analyst (per idea)  +  Format Ideas        (no LLM)
          │
[LLM 3] Competition Analysis ── 3 × { idea_id, competitors[], market_gap_summary }
          │
   Format Ideas                                           (no LLM)
[LLM 4] Feasibility ── 3 × { idea_id, solvability_score, required_apis[], mvp_complexity, reasoning }
          │
   Idea Report (join 2 + 3 + 4 by idea_id) ─┬─> {"ideas": [...]} ─> Chat Output   (no LLM)
                                            └─> 1 doc per idea ─> Save Ideas (Astra DB)
```

Each prompt file lists its node's Prompt Template, Format Instructions
(`system_prompt`), Output Schema table and wiring. After editing one, run
`python flows/build_flow.py --push` (Langflow must be running) to regenerate
`Prometheus.json` and update the "Prometheus" flow in Langflow.

The Query Planner returns exactly one object; Synthesize, Competition
Analysis and Feasibility return exactly 3 (one per idea). Structured Output
wraps multiple objects as `{"results": [...]}`, which the built-in Parser
can't iterate — so per-idea text goes through **Format Ideas**, and every
custom component accepts both shapes.

Tavily budget per run (all searches at `advanced` depth, 2 credits each):
Public Friction 8 (4 sites × 2 queries) + Competition Analyst 6 (3 ideas ×
2 queries) = 14 searches ≈ 28 credits. G2 was dropped: its hits were mostly
vendor marketing copy and category pages, while Capterra's excerpts are
individual user complaints. Academic Problems uses 2-3 SerpAPI searches.

**Novelty memory.** Every run saves its ideas to the Astra DB `ideas`
collection (database `Prometheus`, server-side embeddings). Each document's
text is the problem + target user + solution, which is what gets embedded;
metadata holds the topic, domain, solution type, feasibility, a timestamp
and the full idea JSON. At the start of the next run the Astra search node
retrieves the 12 most similar past ideas for the topic and passes them to
the Query Planner and Synthesize as "ideas to avoid".

The Astra DB nodes reference the token as the Langflow global variable
`ASTRA_DB_APPLICATION_TOKEN` (created at startup from the container env,
mapped from `ASTRA_DB_TOKEN` in `docker-compose.yml`) — never commit a flow
export with a raw `AstraCS:` token in it.

Public Friction searches each site separately (its **Site Groups** setting
maps each domain to a Query Planner field) — one combined `include_domains`
search returns almost nothing but Reddit.

The search components take a `queries` handle (Structured Output JSON, or a
Message with one query per line) plus a `queries_key` naming the field to
read, and return compact text (title / URL / excerpt) as a Message. Raw page
content is off by default (`include_raw_content`) to keep token use low.

Each component is fully self-contained (SerpAPI/Tavily calls inlined
directly, no imports from `backend/`) — Langflow loads component files
through its own bundle-module mechanism rather than a normal Python package
import, so a `sys.path` bridge to `backend/app/tools/*` doesn't reliably
work at runtime. The same search logic also exists in
`backend/app/tools/*.py` for the FastAPI side; the two copies are
intentionally separate runtime environments, so keep them in sync by hand if
the query-building logic changes.

## Running it

```bash
cp .env.example .env   # fill in GEMINI_API_KEY, SERPAPI_KEY, TAVILY_API_KEY at minimum
docker compose up langflow -d
```

The `langflow` service builds from `flows/Dockerfile` (stock Langflow image
+ the two search SDKs), mounts the whole repo read-only at
`/app/project`, and starts Langflow with
`--components-path /app/project/flows/components` (the CLI flag, not the
`LANGFLOW_COMPONENTS_PATH` env var — that env var has a known reliability
issue on recent Langflow versions). On startup Langflow should list
**Academic Problems (SerpAPI Scholar)**, **Public Friction (Tavily)**,
**Competition Analyst (Tavily)** and **Idea Report** in the component
sidebar under the `prometheus` category.

Langflow's Google provider reads `GOOGLE_API_KEY`, not `GEMINI_API_KEY` —
set both in `.env` (same value), or configure the key under Settings → Model
Providers in the Langflow UI.

Each component has a `SecretStrInput` for its API key, but leaving it blank
falls back to `SERPAPI_KEY`/`TAVILY_API_KEY` from the environment (i.e. your
`.env`), since `env_file: .env` is wired into the `langflow` service too.

## Importing the flow

Import `Prometheus.json` in the Langflow UI (http://localhost:7860), then
copy its Flow ID into `.env` as `LANGFLOW_FLOW_ID`. After editing the flow in
the UI, export it back over `Prometheus.json` so the repo stays the source
of truth.
